3. La Arquitectura del Proyecto y la Conexión a Base de Datos

3.1. Modelo BaaS (Backend as a Service)

Una pregunta clásica de examen es: "¿Dónde está el servidor de backend? ¿Tienen una API REST en Node.js o Express?".

Tu respuesta clara:
No hay un servidor Node.js intermedio propio. El proyecto utiliza la arquitectura BaaS (Backend as a Service) provista por Google Firebase. La aplicación móvil se conecta directamente a los servicios en la nube de Firebase a través de su SDK cliente oficial en versión modular:

  • Firebase Authentication: Para el registro, inicio de sesión y emisión de tokens seguros.
  • Cloud Firestore: Base de datos NoSQL documental en tiempo real para las alertas, usuarios y tickets.
  • Firebase Storage: Almacenamiento de objetos binarios (imágenes y fotos tomadas con la cámara).

3.2. Desacoplamiento Estricto (Capas Limpias)

Aunque no haya un servidor Express, el código está estrictamente desacoplado siguiendo principios de Clean Architecture:

1. Presentación (UI)

Carpeta app/ y components/. Solo se encargan de renderizar pantallas, capturar eventos del usuario y mostrar estados visuales (carga, error, éxito).

2. Servicios de Datos

Carpeta services/. Contiene la lógica pura de negocio y las llamadas a Firebase. La UI nunca hace queries a Firestore directamente.

3. Modelos y Contratos

Carpeta types/. Interfaces TypeScript estrictas (Pet.ts, User.ts, Ticket.ts) que definen cómo luce cada dato.

4. Utilidades y Helpers

Carpeta utils/. Funciones puras (formateo de WhatsApp, validación geográfica, conversión de monedas y fechas).

3.3. El Patrón Singleton en la Conexión (ConexionFirebase.ts)

El corazón de la infraestructura es el archivo services/ConexionFirebase.ts. Implementa el patrón de diseño creacional Singleton. 

// services/ConexionFirebase.ts (Extracto clave)
export class ConexionFirebase {
  private static instancia: ConexionFirebase | null = null;
  private readonly app: FirebaseApp;
  private readonly auth: Auth;
  private readonly db: Firestore;
  private readonly storage: FirebaseStorage;

  private constructor() {
    // Inicializa la conexión con FirebaseApp y AsyncStorage
  }

  public static obtenerInstancia(): ConexionFirebase {
    if (!ConexionFirebase.instancia) {
      ConexionFirebase.instancia = new ConexionFirebase();
    }
    return ConexionFirebase.instancia;
  }

  public static obtenerFirestore(): Firestore {
    return ConexionFirebase.obtenerInstancia().db;
  }
}
¿Por qué es fundamental el Singleton en un teléfono móvil?
Si cada pantalla o servicio hiciera initializeApp() por su cuenta, el teléfono abriría decenas de conexiones TCP/SSL simultáneas con los servidores de Google. Esto provocaría:
  1. Consumo desmedido de batería y datos móviles del usuario.
  2. Fugas de memoria (memory leaks) por listeners duplicados.
  3. Pérdida de sincronía en el estado del usuario autenticado.
Con el Singleton garantizamos que solo existe una única conexión compartida viva durante toda la ejecución de la app.

4. Cómo se Hizo el CRUD (Bajo qué concepto y cómo funciona)

CRUD son las cuatro operaciones fundamentales sobre los datos: Create (Crear), Read (Leer/Consultar), Update (Actualizar) y Delete (Eliminar).

En este proyecto el CRUD está completamente implementado y encapsulado en services/mascotasService.ts sobre la colección alertas de Firestore.

4.1. CREATE (Publicar Mascota) → crearAlertaMascota()

Para crear una publicación ocurren varios pasos técnicos coordinados:

  1. Subida de fotos a Storage en paralelo: La función toma las rutas locales del teléfono (file://... o Data URLs base64) y las sube a Firebase Storage con uploadBytes() o uploadString() usando Promise.all() para no hacer esperar al usuario una foto tras otra.
  2. Sanitización de campos (limpiarUndefined): Firestore tira un error fatal si le mandás un campo con valor undefined. Creamos una función recursiva que limpia el objeto antes de enviarlo.
  3. Inyección del autor y timestamp: Se asocia el uid del usuario autenticado (auth.currentUser.uid) y la marca de tiempo oficial del servidor con serverTimestamp().
  4. Inserción en Firestore: Se ejecuta addDoc(collection(db, 'alertas'), payload), que genera un identificador alfanumérico único para el nuevo documento. 
// services/mascotasService.ts
export async function crearAlertaMascota(datos, fotosLocales) {
  // 1. Subir fotos a Firebase Storage
  const urlsFotos = await Promise.all(fotosLocales.map(uri => subirImagenMascota(uri)));
  
  // 2. Limpiar y estructurar payload
  const payload = limpiarUndefined({
    ...datos,
    fotos: urlsFotos,
    creadoPor: auth.currentUser.uid,
    fechaReporte: serverTimestamp(),
  });

  // 3. Guardar en Cloud Firestore
  const docRef = await addDoc(collection(db, 'alertas'), payload);
  return docRef.id;
}

4.2. READ (Listar y Consultar) → listarTodasLasAlertas() y obtenerAlertaPorId()

Para leer la información implementamos consultas modulares y resilientes:

  • Lectura individual: obtenerAlertaPorId(id) usa getDoc(doc(db, 'alertas', id)) para traer una única mascota por su clave primaria.
  • Listado con filtros y orden: listarTodasLasAlertas(filtros) arma dinámicamente un query() con restricciones where('estado', '==', ...), where('especie', '==', ...) y orderBy('fechaReporte', 'desc').
  • Resiliencia contra falta de índices compuestos: Si Firestore rechaza una consulta porque requiere un índice compuesto en la consola de Firebase, el código captura el error y realiza el ordenamiento en memoria (JavaScript sort()) para que la app jamás se caiga ni le muestre una pantalla rota al usuario.

4.3. UPDATE (Modificar Mascota) → modificarAlertaMascota()

Permite editar los datos de una mascota ya publicada (por ejemplo, actualizar la descripción, señas particulares o marcarla como "Encontrado"):

  • Utiliza updateDoc(doc(db, 'alertas', idAlerta), payload).
  • Si el usuario añade fotos nuevas, las sube a Storage y concatena las URLs nuevas con las ya existentes.
  • Inyecta automáticamente el campo fechaModificacion: serverTimestamp().

4.4. DELETE (Eliminar Mascota) → eliminarAlertaMascota()

Ejecuta deleteDoc(doc(db, 'alertas', idAlerta)), borrando el documento de la base de datos de forma permanente.

¡Y hay un segundo CRUD en la app!
En services/soporteService.ts está implementado el CRUD de incidentes técnicos en la colección tickets_soporte:
  • enviarTicketSoporte(input): Crea tickets con título, descripción, tipo de problema y correo.
  • listarTicketsPorUsuario(usuarioId): Lee los tickets asociados al usuario conectado.
¡Podés mencionarlo para demostrar que no solo hiciste CRUD de mascotas sino también de soporte al usuario!

5. NoSQL (Firestore) vs. SQL Tradicional (La pregunta estrella)

Este es uno de los temas conceptuales más importantes de toda la carrera. Tenés que saber explicar con naturalidad cómo se diferencian y cómo impactó esa diferencia en este proyecto.

5.1. Cuadro Comparativo Rápido

Concepto SQL Tradicional (Relacional - MySQL / PostgreSQL) NoSQL (Documental - Cloud Firestore)
Estructura Tablas rígidas con filas (tuplas) y columnas fijas. Colecciones que contienen Documentos (similares a objetos JSON).
Esquema Estricto (Schema-first). Toda fila debe cumplir el tipo de dato definido. Flexible (Schema-less). Un documento puede tener campos que otro documento no tiene.
Relaciones Claves primarias y foráneas (Foreign Keys) con integridad referencial. Referencias lógicas por ID o documentos embebidos/anidados.
Consultas complejas Operador nativo JOIN ejecutado directamente por el motor de BD. No existe el JOIN en el motor. Se resuelve por desnormalización o en la aplicación.
Escalabilidad Vertical (requiere servidores con más CPU y RAM). Horizontal masiva (distribuida en la nube automáticamente por Google).

5.2. Cómo se Vio Esta Diferencia en "Patitas Encontradas"

En una base de datos SQL tradicional, si querés mostrar una alerta con los datos de contacto de su dueño (nombre, teléfono, correo), harías una consulta relacional con JOIN: 

-- En SQL Tradicional:
SELECT alertas.*, usuarios.nombre, usuarios.telefono 
FROM alertas 
JOIN usuarios ON alertas.creadoPor = usuarios.id;

¿Pero qué pasa en Firestore? ¡No existe la sentencia JOIN!
Las alertas están en la colección alertas y los usuarios en la colección usuarios.

¿Cómo lo resolvimos en el proyecto? Con un "Application-Level JOIN" (JOIN a nivel de aplicación)
Fijate en la función listarAlertasConUsuario() de services/mascotasService.ts:
  1. Consultamos las alertas de la colección alertas.
  2. Extraemos la lista de creadoPor (los IDs de los dueños).
  3. Deduplicamos con un Set: Si un vecino publicó 5 mascotas, no hacemos 5 pedidos iguales a la base de datos; pedimos su usuario una sola vez.
  4. Consultamos los perfiles en paralelo usando Promise.all() contra la colección usuarios.
  5. Cruzamos (mapeamos) los datos en memoria con JavaScript y le entregamos a la pantalla el objeto PetConUsuario completo.
// services/mascotasService.ts (Application-Level JOIN)
export async function listarAlertasConUsuario(filtros) {
  const alertas = await listarTodasLasAlertas(filtros);
  
  // 1. Obtener UIDs únicos para evitar consultas repetidas
  const uidsUnicos = Array.from(new Set(alertas.map(a => a.creadoPor).filter(Boolean)));
  
  // 2. Traer perfiles de usuarios en paralelo
  const usuariosMap = new Map();
  await Promise.all(uidsUnicos.map(async (uid) => {
    const userSnap = await getDoc(doc(db, 'usuarios', uid));
    if (userSnap.exists()) usuariosMap.set(uid, userSnap.data());
  }));

  // 3. Cruzar los datos en memoria
  return alertas.map(alerta => ({
    ...alerta,
    usuario: usuariosMap.get(alerta.creadoPor) ?? null
  }));
}

5.3. Desnormalización y Datos Embebidos

Otra gran diferencia NoSQL: en SQL, las fotos de una mascota irían en una tabla secundaria fotos_mascota con su clave foránea. En Firestore, aprovechamos la flexibilidad documental y guardamos directamente un arreglo de strings dentro del mismo documento: fotos: ["url1", "url2"], y las coordenadas como un objeto embebido: coordenadas: { latitude: -34.45, longitude: -58.91 }. Esto ahorra consultas y acelera la carga.

6. Sesión, Tokens y Persistencia (¿Cómo sabe la app quién sos?)

En la web es común usar cookies o localStorage. Pero en React Native para celulares, esos mecanismos del navegador no existen por defecto.

6.1. ¿Qué token se usa?

El sistema utiliza JSON Web Tokens (JWT) emitidos y firmados criptográficamente por los servidores de identidad de Google (Firebase Auth). Cuando un usuario se loguea con éxito con email y contraseña, Firebase genera un token de acceso seguro.

6.2. La Persistencia Nativa en AsyncStorage

Para que el usuario no tenga que escribir su usuario y contraseña cada vez que abre la app, en services/ConexionFirebase.ts configuramos la autenticación con persistencia nativa: 

// services/ConexionFirebase.ts
this.auth = initializeAuth(this.app, {
  persistence: getReactNativePersistence(AsyncStorage),
});

Esto le dice al SDK de Firebase: "Guardá el token y las credenciales cifradas en el almacenamiento local del teléfono (AsyncStorage)".

6.3. El Observador Reactivo (onAuthStateChanged) en AuthContext.tsx

En services/AuthContext.tsx vive el contexto global de autenticación. Utiliza el patrón Observer (Observador) provisto por Firebase: 

// services/AuthContext.tsx
useEffect(() => {
  const desuscribir = onAuthStateChanged(auth, async (firebaseUser) => {
    if (firebaseUser) {
      setUsuario(firebaseUser);
      const token = await firebaseUser.getIdToken(); // Obtenemos el JWT
      
      const sesion = { uid: firebaseUser.uid, email: firebaseUser.email, token };
      await AsyncStorage.setItem('user_session', JSON.stringify(sesion));
      
      // Sincronizamos con los datos adicionales de Firestore (nombre, foto, teléfono)
      await sincronizarPerfilUsuario(firebaseUser);
    } else {
      setUsuario(null);
      setPerfilUsuario(null);
      await AsyncStorage.removeItem('user_session');
    }
    setCargando(false);
  });

  return () => desuscribir(); // Limpieza del listener al desmontar
}, []);
El flujo de vida de la sesión (explicado fácil):
  1. Abrís la app: Firebase busca en AsyncStorage si hay un token previo.
  2. Si hay token: Lo valida en segundo plano con Google. Si está por vencer, Firebase lo renueva automáticamente sin molestar al usuario.
  3. onAuthStateChanged se dispara: Le pasa el usuario autenticado al AuthContext y la app te lleva directo al Home (Feed de Mascotas).
  4. Si no hay token: La app te muestra la pantalla de Bienvenida o el Login.
  5. Cerrar sesión: Llamás a cerrarSesion(), que ejecuta signOut(auth) y borra la clave user_session de AsyncStorage.

7. Los Hooks: El Corazón Reactivo de la Aplicación

Los Hooks son funciones especiales de React que permiten a los componentes funcionales "engancharse" al estado interno y a los ciclos de vida del framework sin necesidad de escribir clases complejas.

7.1. Los Hooks Estándar de React que Usamos

  • useState (Memoria local del componente):
    Permite guardar variables que, al cambiar, vuelven a dibujar la pantalla. Ejemplos en el proyecto: const [cargando, setCargando] = useState(true) para el spinner, const [alerta, setAlerta] = useState(null) para la mascota actual, o const [filtro, setFiltro] = useState(0) en el mapa.
  • useEffect (Efectos secundarios y ciclos de vida):
    Ejecuta código cuando el componente aparece en pantalla (montaje), cuando cambia una variable de control o cuando se destruye (desmontaje). Lo usamos para cargar datos de Firebase al entrar a una pantalla o para suscribirnos a onAuthStateChanged.
  • useCallback (Optimización de funciones):
    Guarda la definición de una función en memoria entre renderizados para que no se vuelva a crear desde cero en cada milisegundo. Lo usamos en cargarDetalle() y recargarPuntos().
  • useMemo (Optimización de cálculos pesados):
    Almacena el resultado de una operación costosa. Por ejemplo, en hooks/useMapState.ts, usamos useMemo para calcular filteredPets: solo filtra las mascotas cuando cambia el texto de búsqueda o el chip de filtro, evitando recalcular en cada toque de pantalla.
  • useRef (Referencias persistentes sin redibujado):
    Permite guardar una referencia mutable que no dispara un re-render al modificarse. Lo usamos en mapContainerRef para enviar comandos directos al mapa de Leaflet (hacer zoom, centrar coordenadas) sin redibujar toda la pantalla.
  • useContext (Consumo de estado global):
    Permite acceder a los datos compartidos de un Contexto desde cualquier componente hijo sin tener que pasar propiedades de mano en mano ("prop drilling").

7.2. Nuestros Custom Hooks (Hooks Propios del Proyecto)

Para no repetir código y encapsular la lógica de negocio, creamos dos Custom Hooks fundamentales:

1. useAuth() (services/AuthContext.tsx)

Cualquier pantalla que necesite saber quién es el usuario conectado o cerrar sesión solo escribe:
const { usuario, perfilUsuario, cerrarSesion } = useAuth();
Limpio, elegante y en una sola línea.

2. useMapState() (hooks/useMapState.ts)

Encapsula todo el comportamiento del mapa interactivo: recupera alertas de Firebase, filtra por especie/estado, maneja el buscador en tiempo real, obtiene la ubicación GPS del celular y expone métodos de zoom.

7.3. Hooks de Expo Router y Maquetado

  • useRouter(): Permite navegar programáticamente entre pantallas (router.push('/detalle/123'), router.back()).
  • useLocalSearchParams(): Captura los parámetros dinámicos de la URL (por ejemplo, el id de la mascota en app/detalle/[id].tsx o las coordenadas en /mapa?alertaId=...).
  • useSafeAreaInsets(): Lee el notch superior y la barra de navegación de 3 botones de Android para que los botones de la app no queden tapados.

8. La Jugada Maestra del Mapa (Leaflet + WebView)

Si te preguntan: "¿Cómo implementaron el mapa interactivo? ¿Usaron Google Maps?", tenés una historia brillante para contar:

La justificación de la decisión arquitectónica:
"Originalmente en el ecosistema de React Native se suele sugerir react-native-maps con Google Maps. Sin embargo, Google Maps exige vincular una tarjeta de crédito internacional a Google Cloud, facturación por cada petición a la API, y en emuladores o dispositivos sin Google Play Services la app simplemente falla o muestra una pantalla gris."

"Para garantizar una solución gratuita, robusta, multiplataforma y sin costos ocultos, implementamos un mapa interactivo utilizando Leaflet.js 1.9.4 dentro de un componente react-native-webview con cartografía libre provista por OpenStreetMap y CartoDB Voyager."

¿Cómo se comunican React Native y el Mapa HTML? (El Puente Bidireccional)

El archivo components/map/MapContainer.tsx genera dinámicamente un documento HTML con Leaflet y establece un canal de comunicación bidireccional:

  • De la Web a React Native: Cuando el vecino toca un pin de mascota en el mapa, el JavaScript de Leaflet ejecuta:
    window.ReactNativeWebView.postMessage(JSON.stringify({ type: 'SELECT_PET', petId: '...' })).
    React Native escucha esto a través de la propiedad onMessage del WebView y abre la tarjeta de la mascota seleccionada.
  • De React Native a la Web: Cuando el usuario presiona los botones nativos de "+" (Zoom In), "-" (Zoom Out) o "Mi Ubicación", React Native inyecta comandos con webViewRef.current.injectJavaScript('map.zoomIn();').

9. Hardware Nativo y Contacto Directo por WhatsApp

9.1. Acceso a Hardware Nativo con Expo

  • Geolocalización GPS (expo-location): Solicita permisos en tiempo de ejecución al sistema operativo móvil (requestForegroundPermissionsAsync) y obtiene la latitud y longitud precisa del dispositivo con getCurrentPositionAsync para georreferenciar los reportes.
  • Cámara y Galería (expo-image-picker): Permite al usuario capturar una foto al instante de la mascota encontrada o seleccionarla de la galería, comprimiéndola y enviándola a Firebase Storage.

9.2. Integración con WhatsApp sin Servidores Intermedios (utils/whatsapp.ts)

En vez de gastar recursos implementando un chat interno con WebSockets que nadie usa, aprovechamos la herramienta que todo vecino ya tiene instalada: WhatsApp.

En utils/whatsapp.ts creamos un normalizador inteligente para números telefónicos de Argentina:

  • Limpia caracteres extraños, espacios y guiones.
  • Maneja los formatos locales: remueve el prefijo '0' de salida nacional y el '15' de celular (ej: 011 15... → 54911...).
  • Genera un enlace universal con el protocolo https://wa.me/{telefono}?text={mensaje}.
  • Abre WhatsApp directamente con Linking.openURL() con un texto ya redactado y contextualizado: "¡Hola! Te contacto desde la app Patitas Encontradas respecto a tu publicación sobre 'Firulais' (mascota perdida en Pilar)...".

10. Machete de Respuestas Rápidas para la Mesa Evaluadora

Acá tenés las 8 preguntas más comunes que te pueden tirar los profesores, con la respuesta exacta y al hueso:

1. "¿Qué arquitectura de software usaron en la aplicación?"

"Usamos una arquitectura limpia (Clean Architecture) desacoplada en tres capas principales: Capa de Presentación (pantallas con Expo Router y componentes modulares), Capa de Lógica y Servicios (funciones puras en services/ que encapsulan las llamadas a Firebase) y Capa de Dominio/Tipado (interfaces estrictas en TypeScript). Además, implementamos el patrón Singleton para centralizar la conexión a Firebase."

2. "¿Por qué eligieron una base de datos NoSQL como Firestore en vez de una relacional como MySQL o PostgreSQL?"

"Porque para una aplicación móvil comunitaria prima la velocidad de lectura, la disponibilidad offline nativa y la flexibilidad en los datos. Firestore nos permite guardar arreglos de fotos y objetos de coordenadas GPS embebidos directamente en cada documento sin crear tablas intermedias, y ofrece sincronización en tiempo real sin tener que montar servidores de WebSockets propios."

3. "¿Cómo hicieron para relacionar a los usuarios con sus mascotas si en Firestore no hay JOIN?"

"Lo resolvimos mediante un Application-Level JOIN. Cada alerta guarda el UID del creador. Al listar, extraemos los UIDs únicos con un Set para no repetir consultas, traemos los perfiles en paralelo con Promise.all desde la colección usuarios y fusionamos los datos en memoria con JavaScript antes de renderizar la pantalla."

4. "¿Cómo se maneja la persistencia de la sesión del usuario cuando se cierra la aplicación?"

"Firebase Auth emite tokens seguros JWT. Para persistirlos en móvil, configuramos getReactNativePersistence(AsyncStorage) en el Singleton de Firebase. Al iniciar la app, onAuthStateChanged en nuestro AuthContext verifica automáticamente si hay un token válido en AsyncStorage y restaura la sesión sin pedir login nuevamente."

5. "¿Por qué en el README dice que usan Zustand o React Hook Form si no están en el código?"

"Formaron parte de la propuesta inicial en el backlog. Sin embargo, al desarrollar, priorizamos la simplicidad y la reducción de dependencias externas (principio YAGNI): React Context y los hooks nativos (useState, useCallback, useMemo) cubrieron el 100% de nuestras necesidades con menor sobrecarga y excelente rendimiento nativo."

6. "¿Cómo funciona el mapa interactivo y por qué no usaron la API de Google Maps?"

"Para evitar los costos de facturación en dólares y la dependencia de API Keys de Google Cloud, integramos la librería libre Leaflet.js 1.9.4 dentro de un componente react-native-webview con cartografía de OpenStreetMap y CartoDB. La comunicación entre el mapa y React Native es bidireccional mediante postMessage y injectJavaScript."

7. "¿Qué pasa si un usuario no tiene conexión a internet al cargar el mapa o el detalle?"

"El código cuenta con manejo resiliente de errores. Si Firestore no responde o el dispositivo está fuera de línea, la aplicación no colapsa: utiliza datos en caché local (AsyncStorage) o puntos iniciales de respaldo, e informa amigablemente al usuario mediante banners claros."

8. "¿Dónde se guardan las fotos de las mascotas que saca la cámara?"

"Se guardan en Google Cloud Storage a través de Firebase Storage. La cámara genera un archivo local temporal en el teléfono, nuestro servicio subirImagenMascota() sube los bytes al bucket de Firebase y guarda la URL pública resultante dentro del campo fotos del documento de la mascota en Firestore."
